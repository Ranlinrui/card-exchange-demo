# 可配置卡密服务：分享版介绍

本项目交付一个能在本机运行的演示：客户创建订单，商家人工核实到账，后台再调用固定的上游脚本，客户凭本单查询码看进度与交付。默认全部模拟，别人需要接自己的资源。

## 它解决什么事

把“选商品、留订单、申报付款、人工核款、查原单、交付内容”连成可操作的流程。静态收款图只展示付款入口，不能判断真实到账；客户点击“已付款”只创建核款申请。

客户页有商品选择、目标账号输入和订单查询；商家页有登录、待核款订单、实际到账金额核对和原单查询。模拟商品包括兑换码与账号两类，所有交付都是合成数据。

## 三种需要分清的动作

| 谁做 | 做什么 | 会不会触发采购 |
| --- | --- | --- |
| 客户 | 创建订单、保存查询码 | 不会 |
| 客户 | 申报已付款并填写参考信息 | 不会，只进入待核款 |
| 商家 | 查看真实收款记录，输入相同金额并确认到账 | 会，订单进入处理 |

模拟演练里可以用虚构金额和付款参考练习操作；真实接入后，勾选确认必须基于真实到账记录。

## 别人需要自己准备什么

- 自己的商品与价格，写入本地 `config/products.json`。
- 自己的二维码，放入 `assets/private/`；只在自有上游模式下使用。
- 自己有权使用的进货或交付来源，接入固定本地脚本。
- 新的管理员口令；网页自动化另需自己的 Chrome、账号、页面地址与控件定位规则。

Python 模板与网页自动化模板都只是起点。模板不包含真实供方 API、运营网址、专用页面规则、凭据或登录态。虚构本机上游可以演练，不证明真实网站可用。网页模板目前只支持传统整页表单导航；不刷新整页的局部提交、网页后台任务和持续连接均不能直接套用，需要本人另行适配、验证。

## 为什么遇到未知结果要停

假设上游已经创建了原单，但返回时网络超时。立刻再买一次会有重复采购风险。因此项目先保存本地订单号与提交意图；不明确时转“结果待核实”，商家只能查原单。重启也不会把“提交中”重新采购。

真实网站必须能够按商家订单号可靠找原单；查不到、查失败与仍在处理应能区分。无法区分就需要本人处理，不能凭“按钮点过了”判成功。

## 查询和本地保存

创建订单时只返回一次查询码，客户应立即保存。服务器只保存摘要，查询其他订单不能复用本单码。目标值、付款参考和交付内容会加密保存在本地；自动生成的密钥与数据库一起留在使用者手里。

动态验证码是在浏览器本地按公开标准计算的短时验证码。演示账号使用公开测试种子，不对应任何真实账号。

## 怎么开始

安装 Python 依赖、复制 `.env.example` 为 `.env`，运行 `python server.py`，打开 `http://127.0.0.1:8787`。完整步骤、默认本地演示口令、自有接入配置和测试方式见[README](../README.md)。

[离线图解版](project-introduction.html)提供 10 张界面草案与流程示意，帮助理解各方实际会看到什么。已执行验证范围见[验证记录](validation.md)；没有宣称任何真实支付、真实供方或公网环境已验证。
