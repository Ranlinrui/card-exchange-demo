01

打开就能演练的客户页面

先用虚构商品走完整流程。这里展示的是分享版的功能布局，实际页面以运行结果为准。

默认不采购真实商品

内置脚本只生成合成兑换码和账号内容。

接自己的资源

别人需要自己准备商品、收款图与有权使用的交付来源。

02

客户申报和真实到账，是两件事

静态二维码只提供付款入口。系统无法通过“点了按钮”判断银行或支付账户是否收到钱。

客户操作不会采购

创建订单、提交付款参考都只记录申请。

确认基于真实记录

真正使用时必须由商家核对本人收款渠道。

03

商家确认时，再核对一次金额

只有输入与订单相同的到账金额，并明确勾选本人核实，才会进入处理。

演练与真实使用分开

只有模拟演练可填写虚构金额练习按钮；真实模式必须先核实到账。

不是支付自动对账

没有第三方支付回调或自动退款能力。

04

一单一张查看凭条，别弄丢

客户需要保存订单号和本单查询码，页面不会把所有人的订单列表公开。

自己的订单自己查

只有授权的本单查询响应才解密返回目标与交付。

商家另有登录入口

商家操作还会检查会话与操作校验，不靠客户查询码管理订单。

05

交付的是明确内容，不能把“已点击”当完成

只有上游明确成功并返回完整交付，客户才会看到兑换码或账号信息。

卡密类型 code

返回可展示的兑换文本。

账号类型 account

包含账号、密码和动态验证码种子；本地浏览器计算短时验证码。

06

结果说不清时，先查原单

如果对方已创建订单但返回途中超时，再买一次就可能重复。这里选择停下来核实。

处理中查询有上限

有限等待后仍不明确，就交给商家查询原单。

自己的上游必须能查原单

按商家订单号可靠找回原单，是接入前必须验证的能力。

07

换商品，改本地六个字段

商品文件存在就使用自有配置；没有就读取随仓库提供的示例商品。

金额用整数分

避免填写 1.00 却被理解成 1 分。

不改已创建订单

后续调价只影响新单，旧单保持创建时金额。

08

收款图和自有接入，要成套配置

禁止一边展示自己的收款图，一边仍然只交付模拟内容。

真实到账仍靠本人核对

换成自有二维码也不会获得自动认款能力。

脚本只从固定位置运行

由商家配置 adapters/ 下的 .py 或 .cjs，客户不能传命令。

09

网页自动化是模板，不能包适配所有网站

模板通过浏览器填写与查询本人授权的网页；需要自己的页面规则、账号和 Chrome。

基础演示无需浏览器自动化

Python 模拟流程安装必要依赖即可。

可选 Node + Puppeteer

浏览器与模块路径通过环境传入；私有配置不写公开模板。

10

分享代码，自己的资源留在本地

项目不携带任何其他经营方的供方资源、账号、历史订单或仓库历史。

分享前仍要核文件

忽略规则是辅助，不能代替实际查看待分享文件。
